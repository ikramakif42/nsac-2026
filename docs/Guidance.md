SPHEREx Challenge – Technical Guidance

1. Which SPHEREx data and product should we use?
Use the latest SPHEREx release that is available and supported by the challenge. If QR3 is accessible and its documentation is ready, make it the primary dataset. Keep QR2 as a fallback. Before committing, check the release notes and confirm that the observations needed for the project are actually available. Avoid mixing QR2 and QR3 measurements without accounting for differences in processing and calibration.
For image analysis, start with the Level 2 calibrated spectral image in Multi-Extension FITS (MEF) format. It is more useful than a plain image because it can include the calibrated image, pixel-quality flags, variance and wavelength-related information. The team should inspect the FITS headers and extension names for the selected release rather than assuming every file has exactly the same layout. In particular, SPHEREx uses a linear variable filter, so wavelength can vary across the detector; do not treat the whole image as if it represents one wavelength.
For finding observations, use IRSA’s SIA2 service as the first option for spatial image discovery. Use TAP when more detailed metadata filtering is needed or when checking for recently ingested records that may not yet appear in SIA2. Once the relevant observation is identified, request a spatial cutout instead of downloading the full detector image. This will save time, bandwidth and storage during the hackathon.
In practical terms, the workflow should be: search by sky position and available observation metadata, identify matching files, retrieve a cutout, then process the MEF and retain its coordinate, wavelength and quality information. The exact query fields and cutout parameters should be confirmed against the current IRSA documentation.

2. How should we prepare for the dataset arriving on November 13?
Do not wait for the additional dataset before building the application. Since it is expected on the same day the hackathon begins in Bangladesh, there may be a delay or the files may require some investigation before they can be used. Build the application so that changing the data source does not require changes to the main interface or analysis workflow.
I recommend creating a common internal data structure for observation details, image files, coordinates, observation time, wavelength information and quality data. Then keep separate data connectors for existing SPHEREx releases, the official hackathon dataset and a simulated dataset. Each connector should convert its input into the same internal structure. That way, the team can switch sources through configuration rather than rewriting the application.

Also prepare synthetic FITS files containing known stationary sources, moving sources and variable-brightness sources. Include realistic noise, variance and quality flags where possible. Because the expected source positions and brightness changes are known, these files will help the team check whether its detection and comparison logic is working.
Existing surveys such as WISE, 2MASS or ZTF can be useful for reference or comparison, but they should not be presented as SPHEREx data. Their instruments, wavelength coverage and observing strategies are different. If the official dataset is delayed or inaccessible, use an existing SPHEREx release as the main fallback. Use clearly labelled simulated SPHEREx-like data only to demonstrate parts of the workflow that cannot be tested with the available real observations.
Before the event, ask the organisers for the dataset name and release, file format, sample file, documentation, access method and any authentication requirements. It would also help to know whether the release is an image product, source catalogue, spectral cube or a combination of these. A sample file or schema would let the team prepare the data connector in advance.

3. Should we use Three.js and HEALPix?
Three.js is a reasonable choice for an interactive sky viewer, especially if the team wants users to explore a selected region and move between observation epochs. It can display detected sources, observation footprints and a timeline, and it can make the result engaging to use. However, Three.js should be responsible for rendering only. Astronomical coordinate transformations and measurements should be handled by a scientific processing layer.
The main issue is that right ascension and declination are spherical coordinates, not ordinary screen coordinates. The team should use the image’s World Coordinate System (WCS), for example through Astropy, to map sky positions correctly. For a small field of view, an appropriate projection such as TAN may be suitable. The implementation must also handle right ascension wrapping around at 0/360 degrees, observation times that are not evenly spaced, and gaps where no observation exists.
Be careful when showing apparent movement. A source appearing in different positions does not automatically mean it is a moving object; registration errors, image quality and source-detection uncertainty can also cause differences. Likewise, a brightness change should be assessed using the measurement uncertainties and pixel-quality information. The interface should make it clear when there is not enough evidence to draw a conclusion.
HEALPix is useful for indexing and organising large areas of the sky, particularly for all-sky maps or large-scale searches. It is not necessary for an MVP that retrieves small RA/Dec cutouts. For the first version, use IRSA for data discovery, Astropy WCS for coordinate handling and Three.js (or React Three Fiber) for rendering. Add HEALPix later if the project grows to require efficient all-sky indexing.

Suggested development order
1.	Connect to IRSA and retrieve at least one real SPHEREx observation.
2.	Read the Level 2 MEF and preserve its image, quality, variance and wavelength information.
3.	Build the common data structure and connectors for real, official and simulated datasets.
4.	Display a small sky region and its detected sources.
5.	Add comparison across available observation epochs and wavelength information.
6.	Improve the Three.js viewer after the data workflow is reliable.
My main advice is not to let the 3D interface become the project’s biggest task. A clear, reliable demonstration using genuine SPHEREx observations will be more convincing than a complex visualisation that cannot explain where its data came from or how its results were produced.
